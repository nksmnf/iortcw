# Мультиплеер в iortcw: подробный разбор архитектуры

Документ описывает, как устроена сетевая часть мультиплеера в этом репозитории —
от UDP-сокета до предсказания движения в `cgame`. Все ссылки на код даны
относительно корня репозитория; если не указано иное, речь про дерево `MP/`.

> Репозиторий содержит два независимых дерева исходников: `MP/` (Return to Castle
> Wolfenstein Multiplayer, протокол 61) и `SP/` (одиночная кампания, протокол 50,
> `SP/code/qcommon/qcommon.h:275`). Оба построены на движке id Tech 3, но
> расходятся в игровой логике и в ряде сетевых подсистем. Мультиплеер — это `MP/`.

---

## 1. Общая картина

Движок — классическая клиент-серверная схема Quake 3 с авторитарным сервером:

```
                     ┌──────────────────────── СЕРВЕР ────────────────────────┐
                     │  sv_main.c     — цикл кадра, OOB-пакеты, heartbeat     │
                     │  sv_client.c   — рукопожатие, usercmd, downloads       │
                     │  sv_snapshot.c — PVS-отсечение, дельта-снапшоты        │
                     │  sv_game.c     — мост к VM `qagame`                    │
                     │  sv_world.c    — пространственный индекс сущностей     │
                     └───────────────┬────────────────────────────────────────┘
                                     │  qcommon: msg.c (битовый поток + Huffman)
                                     │           net_chan.c (секвенция, фрагменты)
                                     │           net_ip.c (UDP, IPv4/IPv6, SOCKS)
                                     │
                     ┌───────────────┴──────────── КЛИЕНТ ────────────────────┐
                     │  cl_main.c   — конечный автомат подключения            │
                     │  cl_parse.c  — разбор gamestate/снапшотов              │
                     │  cl_input.c  — генерация usercmd, отправка пакетов     │
                     │  cl_cgame.c  — мост к VM `cgame`, синхронизация времени│
                     └────────────────────────────────────────────────────────┘
```

Три ключевых принципа, унаследованных от Q3:

1. **Авторитарный сервер.** Клиент отправляет только намерения (`usercmd_t`);
   всё состояние мира считает сервер в VM `qagame`.
2. **Ненадёжный транспорт с надёжным поверх.** Всё идёт по UDP. Снапшоты
   принципиально ненадёжны (потерянный кадр не переспрашивается — приходит
   следующий), а строковые команды дублируются до получения подтверждения.
3. **Дельта-сжатие относительно подтверждённого состояния.** Сервер сжимает
   снапшот относительно кадра, который клиент явно подтвердил; клиент сжимает
   `usercmd` относительно предыдущей команды в том же пакете.

## 2. Модули и виртуальная машина

Игровая логика вынесена в три модуля, загружаемые движком через VM-абстракцию
(`MP/code/qcommon/vm.c`):

| Модуль   | Где живёт | Загрузка | Назначение |
|----------|-----------|----------|------------|
| `qagame` | сервер    | `SV_InitGameProgs`, `MP/code/server/sv_game.c:964` | вся игровая логика, правила режимов, урон, объективы |
| `cgame`  | клиент    | `CL_InitCGame`, `MP/code/client/cl_cgame.c:1031` | предсказание, интерполяция, отрисовка мира, HUD |
| `ui`     | клиент    | `CL_InitUI`, `MP/code/client/cl_ui.c:1164` | меню, браузер серверов |

VM умеет три режима (`vm_game`, `vm_cgame`, `vm_ui`; по умолчанию `2`,
`MP/code/qcommon/vm.c:74-76`):

- `0` — нативная динамическая библиотека (`qagame_mac.dylib` и т. п.);
- `1` — QVM-байткод в интерпретаторе;
- `2` — QVM-байткод с JIT-компиляцией (`vm_x86.c`, `vm_armv7l.c`, `vm_sparc.c`,
  `vm_powerpc.c`).

Практический смысл для мультиплеера: **QVM обязателен для pure-серверов**, потому
что нативные библиотеки не проверяются контрольной суммой pk3 и не подлежат
автозагрузке. Сборка модулей управляется `BUILD_GAME_SO` / `BUILD_GAME_QVM` в
`MP/Makefile:26-30`.

Обмен между движком и VM — через таблицу системных вызовов (`SV_GameSystemCalls`,
`CL_CgameSystemCalls`) и экспортов (`gameExport_t`, `MP/code/game/g_public.h:432-470`:
`GAME_INIT`, `GAME_CLIENT_CONNECT`, `GAME_CLIENT_THINK`, `GAME_RUN_FRAME`, …).

## 3. Транспортный уровень

### 3.1. Сокеты — `MP/code/qcommon/net_ip.c`

- IPv4 и IPv6 одновременно; чем именно пользоваться, решает `net_enabled`
  (битовая маска, по умолчанию `3` — оба).
- Порт по умолчанию `27960` (`PORT_SERVER`), мастер-сервер — `27950`
  (`PORT_MASTER`), см. `MP/code/qcommon/qcommon.h:337-341`.
- Поддержан SOCKS5-прокси (`net_socksEnabled` и родственные cvar'ы).
- IPv6-мультикаст для поиска серверов в LAN (`net_mcast6addr`,
  по умолчанию `ff04::696f:7175:616b:6533`).
- **Loopback.** Локальный клиент на listen-сервере не трогает сокеты вообще:
  `NET_SendLoopPacket` / `NET_GetLoopPacket` (`net_ip.c:444-494`) кладут пакет в
  кольцевой буфер. Это значит, что даже одиночная игра по факту проходит через
  весь сетевой стек — сериализацию, дельта-сжатие, предсказание.
- Есть искусственная задержка отправки (`net_dropsim`, `sv_packetdelay`,
  `cl_packetdelay`) — удобно для отладки лагов.

### 3.2. Канал — `MP/code/qcommon/net_chan.c`

`netchan_t` (`MP/code/qcommon/qcommon.h:225-253`) — тонкая надстройка над UDP,
дающая упорядоченность и фрагментацию, но **не** доставку.

Заголовок пакета:

```
[4] sequence        (старший бит = FRAGMENT_BIT, 1<<31)
[2] qport           — только клиент→сервер
[4] checksum        — NETCHAN_GENCHECKSUM(challenge, sequence), кроме legacy-протокола
[2] fragment start  — только у фрагментированных
[2] fragment length — только у фрагментированных
```

Ключевые константы (`net_chan.c:57-62`):

| Константа | Значение | Смысл |
|-----------|----------|-------|
| `MAX_PACKETLEN` | 1400 | максимальный размер датаграммы (запас под MTU 1500) |
| `FRAGMENT_SIZE` | 1300 | полезная нагрузка одного фрагмента |
| `MAX_MSGLEN` | 32768 | максимальный размер логического сообщения (`qcommon.h:208`) |

Что здесь важно понимать:

- **`sequence == -1` означает out-of-band пакет** — это весь «доигровой» трафик:
  `getchallenge`, `connect`, `getinfo`, `rcon`, ответы мастер-сервера.
- **`qport` решает проблему NAT.** Роутер может перевыставить исходный порт
  клиента прямо посреди игры; сервер сопоставляет соединение по паре
  «базовый адрес + qport», а не по порту, и молча обновляет порт.
- **Контрольная сумма от challenge** (`NETCHAN_GENCHECKSUM`) отсекает тривиальный
  спуфинг чужого соединения: не зная выданного challenge, подделать пакет нельзя.
- **Фрагментация выдаётся порциями.** `Netchan_Transmit` отправляет только первый
  фрагмент, остальные уходят из `Netchan_TransmitNextFragment` по мере
  освобождения канала (`net_chan.c:116-183`) — большие сообщения не забивают линию.
  Обратите внимание на хвостовой нюанс: если последний фрагмент оказался ровно
  `FRAGMENT_SIZE`, дополнительно отправляется пустой фрагмент-терминатор.
- Пока у клиента есть неотправленные фрагменты, сервер **пропускает** его снапшот
  (`sv_snapshot.c:860-865`), иначе поехало бы дельта-сжатие.

## 4. Сериализация сообщений — `MP/code/qcommon/msg.c`

### 4.1. Битовый поток и Huffman

`msg_t` — битовый поток, а не байтовый. `MSG_WriteBits` / `MSG_ReadBits`
(`msg.c:110-260`) пишут произвольное число бит, и в обычном (не-OOB) режиме
каждый байт прогоняется через **Huffman-кодер** (`Huff_offsetTransmit` /
`Huff_offsetReceive`, реализация — `qcommon/huffman.c`).

Дерево строится один раз из зашитой таблицы частот `msg_hData`
(`MSG_initHuffman`, `msg.c`), одинаковой на клиенте и сервере, — то есть словарь
не согласовывается, он вкомпилирован. Реальный коэффициент сжатия сервер может
показать сам: `sv_showAverageBPS 1` печатает `cr(...)`/`acr(...)`
(`sv_snapshot.c:885-925`).

OOB-сообщения (`MSG_InitOOB`) идут без Huffman — заголовки netchan и
connectionless-пакеты должны читаться без контекста.

### 4.2. Дельта-сжатие состояний

Основной приём: состояние описывается плоской таблицей полей, каждое ровно 32 бита.

- `entityStateFields[]` (`msg.c:770`, ~72 поля) — для `entityState_t`;
- `playerStateFields[]` (~78 полей) — для `playerState_t`.

Алгоритм `MSG_WriteDeltaEntity` (`msg.c:862-975`):

1. Найти индекс последнего изменившегося поля `lc` — «хвост» неизменных полей
   не передаётся вовсе. Отсюда важное следствие: **порядок полей в таблице влияет
   на трафик** — часто меняющиеся поля стоят в начале.
2. Записать номер сущности (`GENTITYNUM_BITS` = 10 бит), флаг «удалена»,
   флаг «есть дельта», байт `lc`.
3. По каждому полю до `lc` — один бит «изменилось/нет», затем значение:
   - целое поле пишется своим числом бит из таблицы, с отдельным битом «ноль»
     (нули — самый частый случай, и они стоят 1 бит);
   - `float` пишется либо как «ноль» (1 бит), либо как «маленькое целое»
     (`FLOAT_INT_BITS` со смещением), либо как полные 32 бита.

Ассерт `numFields + 1 == sizeof(*from)/4` (`msg.c:877`) — страховка: добавили поле
в `entityState_t`, но забыли в таблицу → падение на старте, а не тихая
рассинхронизация.

`playerState_t` кодируется похоже, но массивы (`stats`, `persistant`, `ammo`,
`powerups`) идут отдельным блоком с битовой маской изменённых элементов.

### 4.3. Дельта команд игрока

`MSG_WriteDeltaUsercmdKey` (`msg.c:644`) — с двумя особенностями:

- `serverTime` кодируется как 8-битная разница относительно предыдущей команды,
  если она влезает, иначе полными 32 битами;
- значения XOR-ятся с **ключом**, который складывается из `checksumFeed` сервера,
  номера подтверждённого сообщения и хеша последней подтверждённой серверной
  команды (`cl_input.c:959-963`, зеркально `sv_client.c:1814-1818`).
  Это не криптография, а барьер против простейших внешних «читов-инжекторов»
  и наивных прокси: чтобы собрать корректный `usercmd`, надо вести всё состояние
  сессии.

## 5. Протокол приложения

Опкоды (`MP/code/qcommon/qcommon.h:194-227`):

**Сервер → клиент (`svc_*`)**

| Опкод | Содержимое |
|-------|-----------|
| `svc_gamestate` | полный слепок: configstrings + baseline-сущности |
| `svc_configstring` | обновление одной configstring (внутри gamestate) |
| `svc_baseline` | базовое состояние сущности (внутри gamestate) |
| `svc_serverCommand` | надёжная строковая команда (номер + строка) |
| `svc_download` | блок файла при UDP-автозагрузке |
| `svc_snapshot` | кадр мира: время, дельта-база, areabits, playerstate, сущности |
| `svc_voipOpus` | голосовой пакет (Opus) |
| `svc_voipSpeex` | legacy, зарезервирован |
| `svc_nop`, `svc_EOF` | заполнитель и терминатор |

**Клиент → сервер (`clc_*`)**

| Опкод | Содержимое |
|-------|-----------|
| `clc_move` | пачка `usercmd_t`, дельта-сжатая, с запросом дельта-снапшота |
| `clc_moveNoDelta` | то же, но клиент просит полный снапшот |
| `clc_clientCommand` | надёжная строковая команда (номер + строка) |
| `clc_voipOpus` | голос |
| `clc_EOF` | терминатор |

### Структура пакета клиент → сервер (`CL_WritePacket`, `cl_input.c:836`)

```
[4] cl.serverId                 — какому gamestate соответствует пакет
[4] clc.serverMessageSequence   — последнее принятое сообщение (база для дельты)
[4] clc.serverCommandSequence   — последняя выполненная серверная команда
    для каждой неподтверждённой команды:
[1] clc_clientCommand [4] номер [string] текст
    опционально:
[1] clc_voipOpus ... голосовые данные
[1] clc_move | clc_moveNoDelta
[1] число команд (≤ MAX_PACKET_USERCMDS = 32)
    N × дельта-usercmd
[1] clc_EOF
```

### Структура пакета сервер → клиент (`SV_SendClientSnapshot`, `sv_snapshot.c:788`)

```
[4] client->lastClientCommand   — подтверждение надёжных команд клиента
    для каждой неподтверждённой серверной команды:
[1] svc_serverCommand [4] номер [string] текст
[1] svc_snapshot
[4] serverTime
[1] lastframe                   — насколько назад дельта-база (0 = полный кадр)
[1] snapFlags                   — SNAPFLAG_RATE_DELAYED / NOT_ACTIVE / SERVERCOUNT
[1] areabytes + areabits        — битовая маска видимых зон BSP
    дельта playerState_t
    дельта-сущности, отсортированные по номеру, терминатор = MAX_GENTITIES-1
    опционально svc_voipOpus
[1] svc_EOF
```

## 6. Установление соединения

Полная цепочка (клиент — `cl_main.c`, сервер — `sv_client.c`):

```
КЛИЕНТ                                     СЕРВЕР
  │ CA_CONNECTING
  │──── OOB "getchallenge <n> wolfmp" ─────►│ SV_GetChallenge   (sv_client.c:60)
  │                                         │  · rate-limit 10/сек на адрес
  │                                         │  · проверка com_gamename ("wolfmp")
  │◄─── OOB "challengeResponse ..." ────────│  · слот в svs.challenges[2048]
  │ CA_CHALLENGING                          │
  │──── OOB "connect \"<userinfo>\"" ──────►│ SV_DirectConnect  (sv_client.c:334)
  │      (сжат Huffman'ом, NET_OutOfBandData)  · бан-лист, GUID, протокол 61
  │                                         │  · валидность challenge, min/maxPing
  │                                         │  · sv_reconnectlimit, пароли
  │                                         │  · GAME_CLIENT_CONNECT в qagame
  │◄─── OOB "connectResponse <challenge>" ──│  · клиент → CS_CONNECTED
  │ CA_CONNECTED, netchan поднят            │
  │──── "new" (надёжная команда) ──────────►│
  │◄─── svc_gamestate ──────────────────────│ SV_SendClientGameState (sv_client.c:737)
  │ CA_PRIMED, грузит карту, стартует cgame │  · клиент → CS_PRIMED
  │──── "cp <serverId> <контрольные суммы>"►│ SV_VerifyPaks_f  (проверка pure)
  │──── первый clc_move ───────────────────►│ SV_ClientEnterWorld (sv_client.c:807)
  │◄─── svc_snapshot ───────────────────────│  · клиент → CS_ACTIVE
  │ CA_ACTIVE                               │
```

Состояния клиента — `connstate_t` (`MP/code/qcommon/q_shared.h:1645-1653`):
`CA_UNINITIALIZED → CA_CONNECTING → CA_CHALLENGING → CA_CONNECTED → CA_LOADING →
CA_PRIMED → CA_ACTIVE`.

Состояния клиента на сервере — `clientState_t` (`MP/code/server/server.h`):
`CS_FREE → CS_ZOMBIE → CS_CONNECTED → CS_PRIMED → CS_ACTIVE`.

Тонкости, о которые обычно спотыкаются:

- **`serverId` — версия gamestate.** Каждый пакет клиента несёт `serverId`.
  Не совпал — сервер игнорирует движения и при необходимости шлёт gamestate заново
  (`SV_ExecuteClientMessage`, `sv_client.c:2057-2075`). Именно это делает
  `map_restart` безопасным. В истории форка есть отдельный фикс эксплойта, где
  подделанный `serverId` сбрасывал игрока (`ff5fd1eb`).
- **Клиенты с LAN-адреса не проходят challenge** (`NET_IsLocalAddress`) и не
  ограничиваются по пингу.
- **`MAX_CHALLENGES` = 2048** с половиной слотов, зарезервированной под несколько
  подключений с одного адреса (`MAX_CHALLENGES_MULTI`, `server.h:229-236`) —
  защита от вытеснения чужих challenge'ей флудом.
- **`challengeResponse` несёт `sv_onlyVisibleClients`** (`sv_client.c:266`) —
  клиент узнаёт про режим ещё до подключения.

## 7. Gamestate и configstrings

`svc_gamestate` — единственное «полное» состояние, которое клиент получает.
Это набор configstrings плюс baseline'ы сущностей (`SV_CreateBaseline`,
`sv_init.c:239`), от которых потом идёт дельта-сжатие, если сущности не было
в предыдущем кадре.

Configstrings — таблица строк на `MAX_CONFIGSTRINGS` = 2048 слотов
(`q_shared.h:1216`), раскладка задана в `MP/code/game/bg_public.h:132-192`:

| Индекс | Назначение |
|--------|-----------|
| 0, 1 | `CS_SERVERINFO`, `CS_SYSTEMINFO` |
| 2, 3 | музыка, сообщение карты |
| 15–29 | **специфика Wolf MP**: `CS_MULTI_INFO`, победитель, описание карты, шесть текстов целей и шесть их статусов |
| 31 | `CS_ITEMS` — битовая строка присутствующих предметов |
| 32 | `CS_SCREENFADE` |
| 36 | `CS_WOLFINFO` — состояние раунда Wolf MP |
| 64+ | `CS_MODELS` (256), `CS_SOUNDS` (256), `CS_PLAYERS` (64), локации, частицы, точки спавна, триггеры целей |

Изменение configstring рассылается как надёжная серверная команда `cs`
(`SV_SetConfigstring` → `SV_SendConfigstring`, `sv_init.c:46-175`); большие строки
режутся на части. `CS_SYSTEMINFO` — отдельная история: там едут `sv_pure`,
списки pk3 и контрольные суммы, и её изменение заставляет клиент
пересобрать список загруженных pk3 (`CL_SystemInfoChanged`, `cl_parse.c:475`).

## 8. Серверный цикл и темп отправки

`SV_Frame` (`sv_main.c:1172`):

1. Накопить `sv.timeResidual`; пока он больше длительности кадра — крутить
   `VM_Call(gvm, GAME_RUN_FRAME, sv.time)`. Длительность задаёт **`sv_fps`
   (по умолчанию 20)**, то есть один игровой тик = 50 мс.
2. Пересчитать пинги (`SV_CalcPings`), проверить таймауты (`sv_timeout` 240 с,
   `sv_zombietime` 2 с).
3. `SV_SendClientMessages` — разослать снапшоты.
4. Отправить heartbeat мастер-серверам.

Защита от переполнения счётчиков: при `svs.time > 0x70000000` (≈23 дня аптайма)
и при приближении `nextSnapshotEntities` к `INT_MAX` сервер сам себя перезапускает
на текущей карте (`sv_main.c:1216-1232`).

Кто и когда получает снапшот (`SV_SendClientMessages`, `sv_snapshot.c:838`):

- **`snapshotMsec` клиента.** Клиент просит частоту через userinfo `snaps`;
  сервер зажимает её сверху значением `sv_fps` (`sv_client.c:1533-1553`).
  Просить 40 снапшотов в секунду с сервера на 20 тиков бессмысленно.
- **Rate control.** Для не-LAN клиентов `SV_RateMsec` (`sv_main.c:1305`) считает,
  прошло ли достаточно времени с прошлого пакета исходя из `rate` клиента
  (зажат в 1000…90000, `sv_client.c:1511-1521`) и `sv_maxRate` сервера, с учётом
  накладных расходов UDP/IP (28 байт для IPv4, 48 для IPv6). Пропущенный по
  этой причине кадр помечается флагом `SNAPFLAG_RATE_DELAYED`.
- **Загружающиеся клиенты снапшотов не получают** — пока идёт UDP-download,
  канал отдан под файл.
- **Ботам снапшот строится, но не отправляется** (`sv_snapshot.c:794-798`):
  ИИ читает состояние напрямую из памяти сервера.

`sv_lanForceRate` (по умолчанию 1) полностью отключает ограничение для LAN-адресов.

## 9. Снапшоты: что клиент вообще видит

### 9.1. Отбор сущностей

`SV_BuildClientSnapshot` (`sv_snapshot.c:619`) → `SV_AddEntitiesVisibleFromPoint`
(`sv_snapshot.c:353`). Для каждой сущности по порядку:

1. Не слинкована в мир (`r.linked`) или помечена `SVF_NOCLIENT` — пропуск.
2. `SVF_SINGLECLIENT` / `SVF_NOTSINGLECLIENT` — адресная фильтрация по получателю.
3. `SVF_BROADCAST` — отправляется всегда, без проверки видимости.
4. **Проверка зон (areaportals).** Если зоны игрока и сущности не соединены
   (закрытая дверь) — пропуск. У сущности хранятся две зоны, потому что дверь
   легитимно стоит на границе.
5. **Проверка PVS.** Кластеры сущности пересекаются с PVS кластера камеры
   игрока; есть отдельная ветка для сущностей, чьи кластеры не влезли в массив
   (`lastCluster`).
6. **Порталы.** `SVF_PORTAL` рекурсивно добавляет всё видимое из точки
   `s.origin2` — так работают зеркала и камеры наблюдения.
7. **Vis-dummy.** RTCW-специфика: `SVF_VISDUMMY` — маленькая невидимая сущность,
   отвечающая за видимость крупного объекта-«хозяина» (`s.otherEntityNum`).
   Нужна для больших моделей, чей центр может быть вне PVS.

Ограничение — `MAX_SNAPSHOT_ENTITIES` = 256 на кадр (`qcommon.h:145`); при
переполнении лишнее отбрасывается, отсортировав по номеру
(`SV_QsortEntityNumbers`). При `MAX_GENTITIES` = 1024 (10 бит на номер,
`q_shared.h:1195-1197`) это вполне достижимо на людной карте.

### 9.2. Дельта-кодирование кадра

`SV_WriteSnapshotToClient` (`sv_snapshot.c:129`) выбирает базу:

- клиент прислал `clc_moveNoDelta` или ещё не активен → полный кадр;
- разрыв больше `PACKET_BACKUP - 3` = 29 кадров → полный кадр
  («Delta request from out of date packet»);
- сущности базового кадра уже вытеснены из кольцевого буфера
  `svs.snapshotEntities` → полный кадр.

Клиентская сторона — `CL_ParseSnapshot` (`cl_parse.c:337`), кольцевые буферы
`PACKET_BACKUP` = 32 кадра и `MAX_PARSE_ENTITIES` = 32 × 256 = 8192 состояний
(`client.h:105`).

Там же считается **пинг**: перебираются последние отправленные пакеты, пока не
найдётся тот, чьё `p_serverTime` сервер уже обработал (`ps.commandTime`), и
берётся разница реального времени. То есть отображаемый пинг — это полный
цикл «команда → обработка → снапшот», а не ICMP RTT.

## 10. Клиентский ввод

`CL_CreateNewCommands` (`cl_input.c:724`) формирует `usercmd_t` — по одной на
кадр рендера, в кольцевом буфере `CMD_BACKUP` = 64 (`cgame/cg_public.h:31`).

`CL_ReadyToSendPacket` (`cl_input.c:765`) решает, пора ли слать: не чаще
`cl_maxpackets` (жёстко зажат в 25…125, по умолчанию 38).

`CL_WritePacket` (`cl_input.c:836`) кладёт в пакет **все команды, начиная с той,
что была в пакете `cl_packetdup` назад** (зажат 0…5). Это ключевая идея:
один потерянный пакет не теряет ввод — команды приедут в следующем. Дубликаты
сервер отбрасывает по `serverTime` (`SV_UserMove`, `sv_client.c:1866-1880`).

Верхняя граница — `MAX_PACKET_USERCMDS` = 32 команды в пакете.

## 11. Предсказание и интерполяция на клиенте

Клиент выводит две разные картинки из одного снапшота:

**Собственный игрок — предсказание.** `CG_PredictPlayerState`
(`MP/code/cgame/cg_predict.c:513`) берёт последний подтверждённый `playerState_t`
из снапшота и **прогоняет заново все ещё не подтверждённые `usercmd`** через
`Pmove` (`MP/code/game/bg_pmove.c`) — тот же самый код, что крутит сервер. Отсюда
критическое требование: `bg_*.c` компилируется и в `qagame`, и в `cgame`, и любое
расхождение немедленно даёт ошибки предсказания.

Ошибка предсказания не применяется рывком, а размазывается на несколько кадров
(комментарий и логика — `cg_predict.c:485-511`). Отключается через
`cg_nopredict` / `cg_synchronousClients` — тогда позиция просто интерполируется.

**Остальные сущности — интерполяция.** `CG_ProcessSnapshots` /
`CG_TransitionSnapshot` (`MP/code/cgame/cg_snapshot.c`) держат пару
«текущий / следующий снапшот» и интерполируют между ними по `cg.time`.

**Синхронизация времени.** `CL_AdjustTimeDelta` (`cl_cgame.c:1121`) ведёт
`cl.serverTimeDelta` — сдвиг между локальным `realtime` и серверным временем.
Логика простая, но с характером:

- разница больше порога (или пауза/рестарт) → мгновенный скачок;
- иначе усреднение `(старое + новое) / 2`, а затем подстройка по 1 мс за кадр;
- если клиент «убежал вперёд» и пришлось экстраполировать
  (`cl.extrapolatedSnapshot`), время откатывается на 2 мс.

`cl_timeNudge` (`cl_cgame.c:1293-1305`) сдвигает `cg.time` вручную: отрицательное
значение уводит клиента назад, увеличивая буфер интерполяции (плавнее, но выше
задержка реакции), положительное — вперёд, в зону экстраполяции (резче, но
дёрганее). Время никогда не идёт назад — есть явный зажим по `cl.oldServerTime`.

## 12. Компенсация задержки — `MP/code/game/g_antilag.c`

Включается через `g_antilag` (по умолчанию **0**, `g_main.c:297`).

Как устроено:

- Каждый игровой кадр `G_StoreClientPosition` сохраняет для активного клиента
  позицию и bbox в кольцевой буфер `clientMarkers[MAX_CLIENT_MARKERS]`
  (10 записей, `g_local.h:519`) вместе с двумя отметками времени —
  игровой (`servertime`) и уточнённой реальной (`time`, с поправкой по
  `trap_Milliseconds` внутри кадра).
- При выстреле `G_HistoricalTrace` (`g_antilag.c:239`) откатывает **всех**
  клиентов на `ent->client->pers.cmd.serverTime` — то есть на момент, который
  стрелявший видел у себя на экране, — делает трассировку и возвращает всех обратно.
- `G_AdjustSingleClientPosition` интерполирует между двумя ближайшими маркерами
  и явно запрещает «лерп в будущее» (`if (time > level.time) time = level.time`).

Компенсируются только хитскан-выстрелы: вызовы `G_HistoricalTrace` живут в
`g_weapon.c:1611` и `g_misc.c:1587` (турель). Снаряды летят обычным способом.

Смежная механика — `G_AttachBodyParts` / `G_SwitchBodyPartEntity`: временная
подмена сущности игрока на отдельные сущности частей тела для более точного
попадания.

## 13. Надёжные строковые команды

Оба направления используют один паттерн: команда получает монотонный номер и
**повторяется в каждом пакете**, пока встречная сторона не подтвердит номер.
Буфер — `MAX_RELIABLE_COMMANDS` = 256 (`qcommon.h:154`, поднято относительно
стокового Q3).

**Сервер → клиент:** `SV_AddServerCommand` / `SV_SendServerCommand`
(`sv_main.c:149-241`). Переполнение буфера — фатально для клиента: его отключают,
потому что тихо потерянная команда рассинхронизировала бы игру.

**Клиент → сервер:** `CL_AddReliableCommand`. Сервер разбирает их в
`SV_ClientCommand` (`sv_client.c:1695`), и здесь несколько защит:

- пропуск в нумерации → `SV_DropClient("Lost reliable commands")`;
- **флудзащита** (`sv_floodProtect`, по умолчанию 1): не чаще одной команды в
  800 мс; лишние молча игнорируются, но пакет обрабатывается дальше — флудер
  лагает сам себя, а не остальных. Исключения (`sv_client.c:1719-1722`):
  `team`, `setspawnpt`, `score` — иначе игра ломалась бы;
- отдельная проверка `reliableAcknowledge` в `SV_ExecuteClientMessage`
  (`sv_client.c:2035-2043`) — без неё поддельный номер заставлял сервер слать
  тысячи «неподтверждённых» команд. Это и есть фикс `bde9322e` в истории форка.

Часть клиентских команд обрабатывает сам движок (`ucmds[]`, `sv_client.c:1640`):
`userinfo`, `disconnect`, `cp`, `vdr`, `download`/`nextdl`/`stopdl`/`donedl`, `voip`.
Всё остальное уходит в `qagame` (`GAME_CLIENT_COMMAND`) — там `say`, `say_team`,
`say_limbo`, `vsay`, `team`, `score`, `follow`, `callvote`, `vote`, `gc` (жалоба)
и отладочные `give`/`noclip`/`god` под `sv_cheats` (`g_cmds.c:2515-2601`).

Серверные команды на клиенте перехватывает `cgame` (`CG_ServerCommand`,
`cg_servercmds.c`): `cs` (configstring), `cp` (центр-принт), `print`, `chat`,
`tchat`, `vchat`, `scores`, `tinfo` (состояние команды), `map_restart`,
`remapShader`, `shake`, `oid` (цели), `complaint`.

## 14. Pure-серверы и автозагрузка контента

**Pure** (`sv_pure`, по умолчанию **1**) означает: клиент обязан подгружать
игровые ресурсы только из тех pk3, что есть у сервера, и в том же наборе.

Механика: сервер публикует контрольные суммы в `CS_SYSTEMINFO`
(`sv_paks`, `sv_referencedPaks`), клиент в ответ шлёт команду `cp` со списком
своих сумм, а `SV_VerifyPaks_f` (`sv_client.c:1296`) проверяет:

- контрольные суммы **cgame и ui** обязаны совпасть с одним из ожидаемых
  pk3-путей (`sv_pureVMPaths`) — то есть игровые модули подменить нельзя;
- в списке клиента не должно быть повторов (иначе можно было бы «набить» его
  одной валидной суммой);
- итоговая сумма должна сойтись с ожидаемой.

Не прошёл — `SV_DropClient("Cannot validate pure client!")`. Пока `cp` не
получена, `SV_UserMove` не обрабатывает движение, а при `CS_ACTIVE` переотправляет
gamestate (`sv_client.c:1832-1841`).

**Автозагрузка** — два пути:

1. **UDP** через сам игровой канал: команды `download`/`nextdl`, блоки
   `svc_download` (`SV_WriteDownloadToClient`, `sv_client.c:957`).
   Скорость ограничена `sv_dl_maxRate` и `sv_dlRate` (по умолчанию 100 — процент
   от `rate` клиента). Медленно, но работает всегда.
2. **HTTP redirect** через libcurl (`MP/code/client/cl_curl.c`): сервер задаёт
   `sv_dlURL`, клиент качает файл оттуда. Битовые флаги `cl_allowDownload` /
   `sv_allowDownload`: `DLF_ENABLE`, `DLF_NO_REDIRECT`, `DLF_NO_UDP`
   (`cl_main.c:2362-2460`).

id-шные pk3 (`pak0` и т. п.) отдавать по автозагрузке запрещено явно
(`sv_client.c:1067`).

## 15. Мастер-серверы, браузер, администрирование

**Heartbeat.** `SV_MasterHeartbeat` (`sv_main.c:243`) периодически шлёт
`heartbeat` на до пяти мастеров (`MAX_MASTER_SERVERS` = 5). Значения по умолчанию:

- `sv_master1` = `wolfmaster.idsoftware.com` (историческое, мёртвое);
- `sv_master2` = **`master.iortcw.org`** — мастер этого форка (`sv_init.c:906`);
- `sv_master3..5` пустые, задаются администратором.

DNS-имена мастеров перерезолвятся раз в 24 часа (`svs.masterResolveTime`).

**Запросы браузера.** Клиент шлёт мастеру `getservers` / `getserversExt`
(вариант с IPv6), получает `getserversResponse` — упакованный список адресов
(`cl_main.c:4777-4870`), затем опрашивает каждый сервер напрямую пакетами
`getinfo` (короткая сводка → `infoResponse`) и `getstatus` (полная сводка с
игроками → `statusResponse`). Локальный поиск — `localservers` (широковещательный
опрос + IPv6-мультикаст).

**Защита от усиления (amplification).** И `getstatus`, и `getinfo`, и
`getchallenge` дают ответ существенно больше запроса, то есть годятся для
DDoS-отражения. Поэтому в `sv_main.c:384-548` реализованы **leaky bucket**
ограничители: по адресу (`SVC_RateLimitAddress`, типично 10 запросов в секунду)
и глобально на исходящий трафик (`outboundLeakyBucket`).

**rcon** (`SVC_RemoteCommand`, `sv_main.c:797`): пароль `rconPassword`, тоже
за rate-limit'ом — и специально так, чтобы словарный перебор был непрактичен.
Пустой пароль = rcon выключен.

**Баны.** `sv_banFile` (по умолчанию `serverbans.dat`), проверка при подключении
(`SV_IsBanned`, `sv_client.c:301`), поддержаны подсети и исключения.

## 16. Боты

Боты в MP — полноценные клиенты сервера, но без сети.

- `SV_BotAllocateClient` (`MP/code/server/sv_bot.c:55`) занимает слот в `svs.clients`
  и ставит `SVF_BOT`; снапшот для них строится, но не отправляется.
- Движение бота формируется как обычный `usercmd_t` и проходит через
  `SV_ClientThink` — тот же путь, что у живого игрока.
- ИИ живёт в двух слоях: **botlib** (`MP/code/botlib/`) — навигация по AAS
  (`be_aas_*`), поиск пути, оружейный и целевой веса, чат-система; и игровой слой
  в `qagame` (`ai_dmnet.c`, `ai_dmq3.c`, `ai_team.c`, `ai_cmd.c`, `ai_chat.c`).
- Управление составом — `g_bot.c`: очередь спавна, `G_CheckMinimumPlayers`
  (добор ботов до `g_minGameClients`, по умолчанию 8), команда `addbot`.

Файлы `ai_cast_*.c` в `MP/code/game/` — наследие SP-кампании (скриптовые NPC);
для мультиплеера они практически не задействованы.

## 17. Голосовая связь (VoIP)

Включена по умолчанию на обеих сторонах (`cl_voip` / `sv_voip` = 1) и
использует **Opus** (`opus-1.2.1` + `opusfile-0.9` в дереве); Speex остался только
как зарезервированный опкод для совместимости.

- Клиент → сервер: `clc_voipOpus` внутри обычного пакета движения
  (`cl_input.c:892-930`), с битовой маской адресатов (`voipTargets`) и флагами
  (`VOIP_SPATIAL` — «слышно всем рядом»).
- Сервер ретранслирует адресатам (`SV_UserVoip`, `sv_client.c:1909`), уважая
  персональные игнор-листы (`SV_UpdateVoipIgnore`) и `SV_ShouldIgnoreVoipSender`.
- Клиент → воспроизведение: `CL_ParseVoip` (`cl_parse.c:830`).
- При записи демо голос собственного микрофона подмешивается в поток
  искусственным `svc_voipOpus`-пакетом (`cl_input.c:900-918`) — иначе своя речь
  в демо не попала бы, сервер её обратно не присылает.

Подробности настройки — `voip-readme.txt` в корне репозитория.

## 18. Демозаписи

Демо — это дословный лог входящих серверных сообщений
(`CL_Record_f` / `CL_PlayDemo_f`, `cl_main.c:728` и `:1098`). Расширение содержит
номер протокола: `.dm_61` (или `.dm_60` для legacy), `DEMOEXT` — `q_shared.h:108`.

Следствия из такого устройства:

- при воспроизведении предсказание отключено — `CG_PredictPlayerState`

- запись может начаться только с полного (не дельта-сжатого) кадра — отсюда
  флаг `clc.demowaiting` и принудительный `clc_moveNoDelta`;
- демо жёстко привязано к версии протокола; список совместимых версий —
  `demo_protocols[]` (`qcommon.h:296`).

Есть также `cl_autoRecordDemo` и экспорт видео (`cl_avi.c`, `cl_aviFrameRate`).

## 19. Античит-механики

Форк несёт несколько слоёв, полезно понимать, что каждый реально даёт:

| Механика | Где | Что делает | Ограничения |
|----------|-----|-----------|-------------|
| `sv_pure` | `sv_client.c:1296` | не даёт подменить cgame/ui и ресурсы | не мешает внешним читам |
| Netchan XOR-обфускация | `sv_net_chan.c:44`, `cl_net_chan.c` | шифрует поток ключом из challenge, номера пакета и текста последней команды | обфускация, не криптография |
| Ключ дельты `usercmd` | `msg.c:644` | то же для команд движения | то же |
| Контрольная сумма netchan | `net_chan.c:280`, `qcommon.h:215` | отсекает спуфинг чужой сессии | — |
| **AWH (anti-wallhack)** | `MP/code/server/sv_wallhack.c` | серверное отсечение невидимых игроков | требует сборки с `USE_ANTIWALLHACK=1` |
| `sv_onlyVisibleClients` | `cl_parse.c:196-208` | клиентское скрытие невидимых игроков | доверяет клиенту |
| GUID | `sv_client.c:366-373` | `cl_guid`, `sv_allowAnonymous` | легко подделывается |

**AWH** заслуживает отдельного описания, потому что это самое содержательное
дополнение форка в сетевой части (`sv_wallhack.c`, 589 строк). Он вклинивается
прямо в отбор сущностей для снапшота (`sv_snapshot.c:549-573`):

1. Для каждого другого игрока `AWH_CanSee` (`sv_wallhack.c:524`) проверяет
   реальную видимость: трассировка к восьми углам bbox (размеры —
   `awh_bbox_horz` 30, `awh_bbox_vert` 60), плюс проверка попадания в поле зрения
   (`player_in_fov`, ограничение по тангажу `MAX_PITCH` 20).
2. Учитывается движение: позиция цели экстраполируется на `PREDICT_TIME` = 0.1 с
   вперёд (`predict_move` / `predict_slide_move` — упрощённая копия физики со
   скольжением по плоскостям и шагами `STEPSIZE` 18), иначе выбегающий из-за угла
   противник появлялся бы с опозданием.
3. Если игрок не виден, но издаёт звук (`has_player_sound`, `sv_snapshot.c:295`)
   и находится ближе `SOUND_HEARING_LIMIT` = 1024 (`AWH_CanHear`), он **всё равно
   отправляется** — но со случайно смещённой позицией (`AWH_RandomizePos`,
   смещение от 10 % до 40 % дистанции в диапазоне 200…1000 единиц). Так звук
   остаётся на месте, а wallhack получает бесполезные координаты.
4. Не применяется к ботам, к наблюдателям и внутри порталов.

Цена — трассировки на каждую пару игроков каждый снапшот; поэтому по умолчанию
`awh_active` = 0, и в `MP/Makefile:259-260` сборка выключена (`USE_ANTIWALLHACK=0`).

Отличие `sv_onlyVisibleClients`: там ту же идею считает **клиент**
(`isEntVisible`, `cl_parse.c:66-165` — семь трассировок: глаза, макушка, центр,
колени и плечи с обеих сторон), выставляя `EF_NODRAW` с гистерезисом 600 мс.
Данные при этом клиенту всё равно приходят, так что от читов это не защищает —
это оптимизация отрисовки, а не античит.

## 20. Специфика Wolf MP поверх движка

Всё, что делает RTCW не «ещё одним Q3», живёт в `qagame` и передаётся через
общий транспорт:

**Режимы игры** (`bg_public.h:196-209`): `GT_FFA`, `GT_TOURNAMENT`,
`GT_SINGLE_PLAYER`, `GT_TEAM`, `GT_CTF`, и собственно вольфенштайновские
`GT_WOLF` (цели), `GT_WOLF_STOPWATCH` (два раунда на время),
`GT_WOLF_CP` (контрольные точки), `GT_WOLF_CPH` (захват и удержание).
По умолчанию `g_gametype` = 5 (`GT_WOLF`).

**Лимбо и волны респауна.** Убитый игрок попадает в лимбо (`PMF_LIMBO`,
`g_client.c:463-576`) и ждёт общей волны возрождения: `g_redlimbotime` /
`g_bluelimbotime` (по 30000 мс). Это меняет весь темп игры относительно Q3 с его
мгновенным респауном. Есть быстрый респаун (`g_fastres`) и ограничение жизней
(`g_maxlives`, `g_axismaxlives`, `g_alliedmaxlives`).

**Цели (objectives).** Тексты и статусы шести целей едут через configstrings
`CS_MULTI_OBJECTIVE1..6` и `CS_MULTI_OBJ1..6_STATUS`, изменения — серверной
командой `oid`.

**Сессия между картами.** `g_session.c` сохраняет команду, класс и статистику
игрока в cvar'ах (`G_WriteClientSessionData` / `G_ReadSessionData`), чтобы
`map_restart` и смена карты не сбрасывали расстановку.

**Голосования** — `callvote` / `vote`, набор разрешённых голосований задаёт
битовая маска `g_voteFlags` (по умолчанию 255 — всё разрешено).

**Жалобы на тимкилл** — команда `gc`, лимит `g_complaintlimit` (3).

## 23. Как это чинилось: заметные исправления в истории форка

Полезно для понимания, где у протокола тонкие места
(`git log -- MP/code/server MP/code/qcommon/net_chan.c MP/code/qcommon/msg.c`):

- `bde9322e` — эксплойт DoS через некорректный `reliableAcknowledge` клиента:
  сервер уходил в рассылку тысяч «неподтверждённых» команд.
- `ff5fd1eb` — эксплойт со сбросом игрока подделанным `serverId`.
- `260c39a2`, `121c3052`, `4a234efe` — переполнение буфера и знаковые операции
  в `MSG_ReadBits` / `MSG_WriteBits`, чтение последнего байта в `MSG_Read*String*`.
- `a47a0d1d` — клиент ошибочно кикался как «unpure» при отсутствии свежих
  cgame/ui pk3.
- `069725dc` — listen-сервер слал снапшоты на каждом клиентском кадре.
- `7f03bcdc`, `d6c2050b` — кеш адресов мастер-серверов и лишние DNS-резолвы.

Общая закономерность: почти все дыры — в разборе недоверенного ввода
(`msg.c`, `sv_client.c`). Любая правка протокола требует симметричной проверки
границ на приёмной стороне.

## 24. Практические выводы

- **Точка входа для понимания «как летит один кадр»:** `SV_Frame` →
  `SV_SendClientMessages` → `SV_BuildClientSnapshot` → `SV_WriteSnapshotToClient`,
  и симметрично `CL_ParseSnapshot` → `CG_ProcessSnapshots` → `CG_PredictPlayerState`.
- **Менять `entityState_t` / `playerState_t` без правки таблиц в `msg.c` нельзя** —
  ассерт поймает на старте, но только если пересобраны и движок, и модули.
- **`bg_*.c` — священная граница.** Расхождение между сервером и `cgame`
  моментально выливается в ошибки предсказания.
- **Протокол 61 несовместим с оригинальным 60** — совместимость даёт
  `com_legacyprotocol` (`LEGACY_PROTOCOL`), при котором отключается
  checksum в netchan.
- **Для соревновательной игры** имеет смысл включать `g_antilag 1`
  (по умолчанию выключен) и поднимать `sv_fps`; для публичных серверов —
  оставлять `sv_pure 1`, задавать `sv_dlURL` и `rconPassword`.
